# PROTOCOL — протокол взаимодействия DS ↔ DSH

## 1. Роли

### DS (планировщик, бесплатная модель)
- Читает `README.md` и, при необходимости, код проекта.
- Пишет и дополняет `docs/PLAN.md` — подробный, пошаговый, самодостаточный.
- Не выполняет шаги плана сам.
- Не экономит токены: план должен быть таким, чтобы DSH ничего
  не додумывал.
- При появлении новой задачи — дописывает шаги в конец `PLAN.md`
  (не перезаписывает).

### DSH (исполнитель, платная модель, DeepSeek Harness)
- Работает в workspace `/var/www/html/sbp_mq_dev`, имеет полный доступ
  к файлам (чтение, запись, удаление, git, запуск команд).
- Читает `docs/PROTOCOL.md` (этот файл) и `docs/PLAN.md`.
- Выполняет шаги плана последовательно.
- После каждого шага пишет результат в `docs/RESULT.md`.
- В чат пишет только короткие статусы.
- Экономит токены: не анализирует проект сверх текущего шага;
  не рефакторит «заодно»; не переспрашивает.

## 2. Файлы

### `docs/PLAN.md` — создаёт и дополняет DS

Единственный источник задач для DSH. Формат — для каждого шага:

    ## Шаг N. <короткое название>

    **Что делать:** <конкретное действие>

    **Файл(ы):** <какие файлы создать/изменить/удалить>

    **Ожидаемый результат:** <что должно получиться>

    **Как проверить:** <команда или критерий>

Шаги нумеруются сквозняком (1, 2, 3, ...). Если DS дописывает план
после того, как часть шагов выполнена, — нумерация продолжается
с последнего номера в `PLAN.md`.

### `docs/RESULT.md` — создаёт и дополняет DSH

Журнал выполнения. Формат — для каждого шага:

    ## Шаг N. <название из PLAN.md>

    **Статус:** выполнено | ошибка

    **Что изменилось:** <файлы, краткое описание>

    **Проверка:** <результат проверки из плана>

    **Примечание:** <если есть; при ошибке — причина>

## 3. Ключевое: DSH сам читает файлы

DSH — не «генератор кода по спецификации». Он читает существующие
файлы в workspace (`sbp.py`, модули, тесты, конфиги) и правит их
по шагам плана.

Поэтому в `PLAN.md` не встраивается готовый код. План описывает:
- что сделать (словами),
- какие файлы затронуть,
- какой ожидается результат,
- как проверить.

DSH сам решает, какой код написать, — опираясь на прочитанные файлы
проекта и на существующие соглашения кодовой базы.

Исключение: если шаг требует точного текста (сообщение коммита,
строка в конфиге, имя файла, ключ Redis) — DS вставляет его в план
дословно.

## 4. Правила для DSH (исполнителя)

1. Прочитай `docs/PLAN.md`. Это единственный источник задач.
2. Если `PLAN.md` не существует или пуст — ничего не делать, написать
   в чат: `PLAN.md пуст, работа не требуется`. Завершить.
3. Если все шаги из `PLAN.md` уже отмечены в `RESULT.md` как выполненные
   — ничего не делать, написать в чат: `План уже выполнен`. Завершить.
4. Выполняй шаги последовательно, начиная с первого невыполненного.
5. Перед шагом — прочитай только те файлы, которые нужны для шага.
   Не читай проект целиком.
6. После каждого шага — обязательно запиши его в `docs/RESULT.md`.
   Шаг считается выполненным только тогда, когда записан в журнал.
   Файлы — врозь, журнал — вслед. Если записать забыл, а пошёл дальше —
   вернись и допиши, прежде чем продолжать.
7. Если `docs/RESULT.md` не существует — создай его. Заголовок файла:
   `# RESULT — журнал выполнения плана`. Отсутствие файла — не повод
   пропустить запись, а повод его создать.
8. Если папки, которая нужна для шага, не существует — создай её.
   Отсутствие папки — не повод остановиться или пропустить шаг.
9. В чат пиши только короткие статусы: `Шаг N: выполнено`.
10. При ошибке:
    - остановиться;
    - записать в `RESULT.md` статус `ошибка` с причиной;
    - написать в чат: `Ошибка на шаге N: причина`;
    - завершить работу.
11. Когда все шаги выполнены — записать финальный статус в `RESULT.md`,
    написать в чат только: `План выполнен`.

### Что DSH НЕ делает

- Не анализирует проект сверх текущего шага.
- Не рефакторит «заодно» — только то, что сказано в шаге.
- Не меняет `PLAN.md` (это файл DS).
- Не переспрашивает — если в плане неясно, это ошибка DS; DSH фиксирует
  это в `RESULT.md` как ошибку шага.
- Не коммитит в git, если в шаге плана явно не сказано иное.
- Не трогает прод-конфиги, секреты и доступы без явного указания
  в шаге.
- **Сверяется с `docs/pitfalls.md`.** Перед правкой модуля — быстро
  пробегает записи по теме: не наступает ли на уже известную граблю.
  Если наступил на **новую** — дописывает запись **в конец**
  `docs/pitfalls.md` по шаблону оттуда:
  «симптом → причина → как не наступить → дата». Старые записи
  не редактирует.

### Что не делать без обсуждения (опасные зоны проекта)

**Конкретные опасные зоны — в `docs/pitfalls.md`.** Перед правкой
модуля DS/DSH открывает файл и проверяет по теме. Плюс общие:

- **Секреты и прод-конфиги.** `.env`, доступы к Redis/MQ, ключи банков,
  сертификаты.
- **API-контракты.** Схемы запросов/ответов FastAPI, переименование
  полей, смена статус-кодов.

## 5. Правила для DS (планировщика)

1. Читать `README.md` и, при необходимости, код.
2. Писать план в `docs/PLAN.md` — подробно, по шагам, с проверками.
3. Каждый шаг — атомарный: одно действие с ясным критерием проверки.
4. Указывать точные пути файлов и точные команды для проверки.
5. Не встраивать готовый код в план (DSH прочитает файлы сам).
   Дословно — только то, что требует точности: сообщения коммитов,
   строки в `.gitignore`, имена файлов, ключи Redis/MQ.
6. **Сверяться с `docs/pitfalls.md`.** При планировании — открыть
   файл, посмотреть, нет ли уже записанной грабли по теме задачи.
   Если шаг плана может наступить на известную граблю — либо обойти
   её в плане, либо явно упомянуть в шаге («не наступать на граблю
   X из pitfalls.md»).
7. Если задача требует продолжения — дописывать шаги в конец `PLAN.md`,
   не перезаписывать.
8. Не экономить токены: план должен быть самодостаточным.

## 6. Цикл работы

1. Пользователь ставит задачу DS.
2. DS читает `README.md`, при необходимости — код, пишет/дополняет
   `docs/PLAN.md`.
3. DS убеждается, что `docs/RESULT.md` существует (создаёт при
   необходимости — пустую шапку).
4. Пользователь отправляет DSH одну строку:
   `Прочитай docs/PROTOCOL.md. Ты DSH. Дальше по протоколу.`
5. DSH выполняет план, дополняет `docs/RESULT.md`, пишет короткие
   статусы.
6. Если нужен новый этап — снова DS дописывает `PLAN.md`, снова DSH
   выполняет.

## 7. Контекст проекта (кратко, для DSH)

Проект **sbp_mq_dev** — FastAPI-сервис получения QR-кодов СБП
(мультибанковое). Точка входа — `sbp.py`. Использует **Redis** и
**MQ** (очередь сообщений).

Документы проекта:
- `README.md` — общее описание, запуск, архитектура.
- `docs/pitfalls.md` — **грабли проекта**: неочевидные механизмы,
  приводящие к багам. Формат: симптом → причина → как не наступить →
  дата. Дописывается в момент, когда грабля наступила.
